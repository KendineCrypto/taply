# Phase 2B: native Instant Pay (proposed deployment review record)

Implementation is authorized by the Phase 2B request. Deployment/security approval
is **not** granted. No Testnet keys, signing, deployment or funds are used by the
local test suite; disposable sandbox accounts are test fixtures only.

* Recipient creates immutable `taply.intent.v1` terms. IDs and hashes use the
  frozen domain-separated JCS algorithm. Retaining every record permanently also
  retains consumed creator/nonces; all duplicate creations fail, including exact
  repeats. Unknown wallet outcomes require reading the same deterministic ID.
* Only direct predecessor = signer calls may create, fund, cancel or retry.
  Funding accepts exactly principal, with no fee/storage deduction. Only native
  Instant terms without merchant/session bindings are enabled in this phase.
* Reserve the operation and increment its nonce before scheduling a native
  transfer to the immutable recipient. Only a private callback with exactly one
  runtime promise result and the matching in-flight nonce can resolve it.
* A recorded failed transfer permits recipient-only, same-destination retry.
  Unknown results, callback panic/out-of-gas, missing callback and stale callbacks
  never authorize another transfer. There is no admin override or refund branch.
  Successful transfer + failed callback can remain unresolved permanently.
* Store mutable fields at fixed serialized size, including a padded payer account.
  Charge an exact per-request permanent storage bond for key, record and protocol
  overhead. Check the actual storage delta on creation, and unchanged size on every
  transition. No speculative 4096-byte reserve. No storage withdrawals/refund
  promises: records/nonces are intentionally retained. Runtime rejection refunds
  attached deposits according to NEAR receipt rules (verified in sandbox).
* Separate cumulative received principal, callback-confirmed payouts, failed-held
  principal and in-flight principal: received = confirmed + failed-held + in-flight.
  In-flight is an unresolved outgoing exposure, NOT necessarily contract cash:
  the transfer may already have succeeded. Require cash for storage plus all
  failed-held obligations plus each new outgoing transfer. Never collateralize a
  new transfer from a different held obligation. Authentication yocto deposits are
  tracked separately. No fees, treasury withdrawal, relayer or custodial key API.
* Caller prepays execution/promise gas; principal is never used as a gas budget.
  Fixed callback gas, minimum initiating gas and measured worst-case usage must be
  published with the sandbox evidence before a deployment proposal. Deployer must
  separately fund code/base-state storage and operational balance. Gas refunds and
  contract execution rewards are protocol balance effects, not payment principal.
* Protected Pay, Handshake, tokens and upgrades/migrations are absent. A contract
  account full-access key could still replace code; deployment authority policy,
  code hash pinning and an in-flight upgrade prohibition require human review.

Review gates: actual storage/gas measurements; adversarial sandbox results;
callback-stall limitation; external receipt verifier and wallet integration;
explicit approval of any Testnet deployment/signing/fund movement.

## 2. Roles and key custody (pilot policy)

- **Operator:** one named human. Creates the account, holds its only key, signs
  the deployment. Not an agent, not CI.
- **Dedicated account:** a fresh Testnet account used only for this contract
  (for example `taply-pay-pilot-1.testnet`; final name not chosen). Never a
  personal account or one that holds other keys, contracts or funds.
- **One FullAccess key, retained.** Generated by the operator's wallet or
  `near-cli-rs` on the operator's machine, stored in a password manager or
  hardware wallet. Never in the repository, CI, the frontend, a screenshot, a
  chat or a shared drive. No function-call keys are added.
- The key is **not used** after deployment unless the lead declares an incident.
  Any use is visible on chain (the access-key nonce changes), and the receipt
  verifier then refuses to verify payments in that window
  (`CONTRACT_ACCOUNT_ACTIVITY`).

## 3. Risks of retained upgrade authority (must be accepted explicitly)

Keeping a FullAccess key means the contract is **not immutable**. Whoever holds
that key can, in a single transaction:

1. **Replace the code.** New code can transfer the whole contract balance,
   including failed-held principal and storage bonds, to any account; rewrite
   any stored request (for example mark one FINAL_PAID or change a recipient);
   or brick the contract. The contract has no on-chain defence against its own
   account.
2. **Delete the account** (`DeleteAccount`), sending the remaining balance to a
   beneficiary and erasing all records and obligations.
3. **Add more keys,** including function-call keys or a second FullAccess key.

Consequences and what limits them:

| Risk | Limitation in place | Residual risk |
|---|---|---|
| Key theft = total loss of everything the contract holds | Testnet only, no real value; small pilot balances; key never online in shared systems | A stolen key can still drain Testnet funds and destroy records |
| Silent code swap | The frontend reads the code hash at the same final block as every view and refuses any other hash; the receipt verifier checks the code hash at every block where contract code ran and the key nonces from before funding to the state block | A swap between the frontend's last read and a wallet signature cannot be excluded; a swap-and-restore is caught by the verifier only for payments it verifies |
| Upgrade with in-flight payouts | There is no upgrade path in the code and no migration; any redeploy is an unreviewed change | Redeploying with a different Borsh layout can make every stored record unreadable, including PAYOUT_IN_FLIGHT and failed-held principal |
| Users must trust the operator | Documented here; Verified Paid requires receipt evidence, not operator claims | Recipients and payers cannot prevent operator actions |

Exit options after the pilot (each needs a separate human decision): delete the
last key in a reviewed transaction (code becomes immutable, no recovery, no
upgrade), move control to a reviewed multisig, or retire the account and deploy
to a new one.

## 6. Read-only checks after deployment (repeatable monitoring)

Run `deploy-preflight.mjs post` on a schedule (for example hourly during the
pilot) and on every incident report. Investigate immediately if any of these
change: code hash, access-key list or a key nonce, `testFaultBuild`,
capabilities, or `received ≠ paid + failed-held + in-flight`. A changed key nonce
means the retained key signed something.

## 7. Emergency shutdown — what is and is NOT possible

| Lever | Effect | Limits |
|---|---|---|
| Frontend kill switch (`NEXT_PUBLIC_TAPLY_FLAG_INSTANT_PAY=off`, redeploy the web app) | Taply's UI stops offering signatures; reads continue | Only affects Taply's UI. Anyone can still call the contract directly with any wallet or CLI |
| Remove contract env variables | Taply stops reading the contract | Same; on-chain state is unchanged |
| Automatic fail-closed | A different code hash, a fault build or an unexpected capability disables payments in the UI without human action | Only in Taply's UI |
| Contract pause | **Does not exist.** There is no pause, admin, refund or settlement method | — |
| Redeploy code with the retained key | Technically possible | Unreviewed code is itself an incident; no migration exists; it breaks the frontend pin (UI fails closed) and every verifier check spanning that block |
| Refund in-flight principal | **Not possible.** PAYOUT_IN_FLIGHT after a successful transfer and a failed callback stays unresolved | The recipient may already hold the funds; never pay again |
| Delete the key | Makes the code immutable | Does not stop the contract or move funds |

Incident routine: switch the frontend flag off, stop new requests, collect
transaction hashes and receipt outcomes (`tx_status` with `wait_until: FINAL`),
`get_request` and `get_accounting`, and do not ask payers to retry. A fixed
contract goes to a **new** account after review.

## 8. What the preflight cannot check

It cannot see the operator's key custody, cannot prove the RPC is honest (same
trust model as the app), cannot detect a code swap-and-restore between two of its
runs, and does not validate wallet behaviour. Use a reviewed RPC provider, run it
from the operator's own machine, and compare with a second provider when in doubt.
